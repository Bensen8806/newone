1. SYSTEM OVERVIEW
================================================================================

A role-based, transparent web application that digitalises the complete lifecycle
of an event at NSSCE — from a club head's initial idea to a student's downloaded
certificate — eliminating paper trails, reducing scheduling conflicts, and
ensuring institutional accountability.

2. STAKEHOLDER & ROLE ANALYSIS
================================================================================

2.1 ROLE HIERARCHY
------------------
  PRINCIPAL       <- Final authority
  HODs            <- Department & venue gatekeepers
  CLUB HEADS      <- Event initiators
  STUDENTS        <- Consumers & participants
  ADMIN           <- System administrator

2.2 ROLE DEFINITIONS
--------------------
  Principal  : Head of NSSCE. Final approver for all events.
  HOD        : Head of a Department (7 departments). Approves venue requests
               within their dept; also creates dept-level events.
  Club Head  : Student leader of a registered club. Creates and submits event
               proposals.
  Student    : Enrolled student at NSSCE. Views events, registers, receives
               certificates.
  Admin      : Manages user accounts, roles, departments, venues.

4. COMPREHENSIVE WORKFLOW
================================================================================

4.1 EVENT LIFECYCLE STATE MACHINE
----------------------------------

  [DRAFT]
     |
     | Club Head submits
     v
  [PENDING_HOD_REVIEW]
     |
     |--- REJECT ---> [REJECTED_BY_HOD] ---> Notification + Remark --> Club Head
     |
     |--- APPROVE --->
                    [PENDING_PRINCIPAL_REVIEW]
                       |
                       |--- REJECT ---> [REJECTED_BY_PRINCIPAL] --> Club Head
                       |
                       |--- APPROVE --->
                                      [APPROVED — PUBLISHED]
                                         |
                                         | Students register
                                         v
                                      [ONGOING / EVENT DAY]
                                         |
                                         | Attendance marked
                                         v
                                      [COMPLETED]
                                         |
                                         | Certificates generated
                                         v
                                      [ARCHIVED]

  Note: Club Head can EDIT and RE-SUBMIT after any rejection.

4.2 STEP-BY-STEP WORKFLOW
--------------------------

  STEP 1 — Club Head: Event Proposal Creation
  -------------------------------------------
  1. Club Head logs in -> navigates to "Create New Event"
  2. Fills in:
     - Event Title, Description, Category (Technical/Cultural/Sports/Social)
     - Target Audience (All / specific year / specific dept)
     - Proposed Date & Time (start + end)
     - Expected Attendance
     - Special Requirements (equipment, catering, external speakers, etc.)
     - Resource Persons / Speakers (if any)
     - KTU Activity Points applicable? (yes/no + category)
  3. Opens Interactive Campus Map -> selects an available venue
     - Map highlights only venues AVAILABLE in selected time slot
     - Hovering shows venue details (capacity, features, owning dept)
  4. Submits -> system auto-identifies the HOD of the venue's department
  5. Status changes to PENDING_HOD_REVIEW
  6. Club Head receives submission confirmation

  STEP 2 — HOD: Venue Request Review
  ------------------------------------
  1. HOD receives in-app notification + email
  2. Reviews full event proposal
  3. Checks venue conflicts, departmental concerns (exams, dept events)
  4. Adds a MANDATORY REMARK (positive or constructive)
  5. Action:
     - APPROVE -> status: PENDING_PRINCIPAL_REVIEW, Principal notified
     - REJECT  -> status: REJECTED_BY_HOD, Club Head notified with remark

  STEP 3 — Principal: Final Approval
  ------------------------------------
  1. Principal receives in-app notification + email (HOD-approved events only)
  2. Reviews full proposal + HOD's remark
  3. Adds own MANDATORY REMARK
  4. Action:
     - APPROVE -> status: APPROVED, event published to all users
     - REJECT  -> status: REJECTED_BY_PRINCIPAL, Club Head notified with
                  both HOD remark and Principal remark

  STEP 4 — Club Head: Post-Decision Actions
  ------------------------------------------
  - If Approved : View published event, share, mark attendance later
  - If Rejected : Edit and re-submit as new draft (old trail preserved)

  STEP 5 — Students: Discovery & Registration
  ---------------------------------------------
  1. Browse Event Calendar (all approved events)
  2. Filter by: Date / Department / Category / Club / Venue / Activity Points
  3. Click event -> view full details
  4. Click "Register" -> system records registration
  5. Pre-event: Reminder notification (1 day before)

  STEP 6 — Event Day: Attendance
  --------------------------------
  1. Club Head / Faculty coordinator marks attendance for registered students
  2. System records attended vs registered-but-absent

  STEP 7 — Post-Event: Certificate Generation
  ---------------------------------------------
  1. Club Head marks event as Completed after event end time
  2. System auto-generates certificates:
     - All attendees    -> "Certificate of Participation"
     - Specific students (manually added) -> "Certificate of Completion"
  3. Students log in -> My Certificates -> download PDF

4.3 HOD APPROVAL ROUTING (VENUE -> HOD MAPPING)
-------------------------------------------------
  Venue Selected           | Approval Goes To
  -------------------------|----------------------------
  Main Auditorium          | Admin HOD / Principal

5. FUNCTIONAL REQUIREMENTS
================================================================================

5.1 AUTHENTICATION & AUTHORIZATION
------------------------------------
  FR-01 : Users log in with college email (@nssce.ac.in or
           @student.nssce.ac.in)
  FR-02 : Role-based access control (RBAC) enforced throughout
  FR-03 : Admin can assign/change user roles
  FR-04 : Session management with secure logout
  FR-05 : Password reset via email

5.2 EVENT MANAGEMENT
---------------------
  FR-06 : Club Heads can create, edit (before submission), and view own events
  FR-07 : Events have mandatory KTU Activity Points category field
  FR-08 : No booking for a venue with conflicting approved event in same window
  FR-09 : Club Heads can re-submit rejected events after editing
  FR-10 : Full audit trail (approver, action, remark, timestamp) visible to all

5.3 VENUE & MAP SYSTEM
-----------------------
  FR-11 : Interactive SVG map of NSSCE showing all bookable venues
  FR-12 : Each venue shows real-time availability:
           - GREEN  : Available (no conflicts)
           - YELLOW : Pending (has a pending approval request)
           - RED    : Booked (confirmed approved event)
  FR-13 : Clicking a venue shows details and mini availability calendar
  FR-14 : Time-slot conflict detection enforced at database level

5.4 APPROVAL WORKFLOW
----------------------
  FR-15 : HOD sees only requests for venues in their department
  FR-16 : Remark field is mandatory for both approval and rejection
  FR-17 : Principal sees only HOD-approved requests
  FR-18 : Rejected events display exact rejection remark prominently to Club Head
  FR-19 : Re-submission creates new approval trail (old trail preserved)

5.5 STUDENT REGISTRATION
-------------------------
  FR-20 : Students can register for any approved, upcoming event
  FR-21 : Students can unregister up to 24 hours before the event
  FR-22 : Maximum capacity enforcement (no registration beyond venue capacity)
  FR-23 : Waitlist system when capacity is full
  FR-24 : Students see registered events on their profile dashboard

5.6 CERTIFICATE SYSTEM
-----------------------
  FR-25 : Certificates auto-generated as PDF after event completion
  FR-26 : Each certificate includes:
           - Student name, Roll number
           - Event name, Date, Venue
           - Issuing authority (NSSCE)
           - KTU Activity Points category
  FR-27 : Certificates include a unique QR code for verification
  FR-28 : Two types:
           - PARTICIPATION : for all attendees
           - COMPLETION    : for specific achievers (manually assigned)
  FR-29 : Students download certificates from their profile

5.7 TRANSPARENCY & NOTIFICATIONS
----------------------------------
  FR-30 : Public event pipeline board shows all events and current status
           (visible to all logged-in users)
  FR-31 : In-app notifications for: submission, approval, rejection,
           registration confirmation, event reminders
  FR-32 : Email notifications for critical actions (approval/rejection)
  FR-33 : Full audit log visible to all users

5.8 KTU ACTIVITY POINTS INTEGRATION
-------------------------------------
  FR-34 : Each event tagged with KTU Activity Points category
  FR-35 : After completion, system generates consolidated activity points
           report per student (exportable as PDF/Excel for KTU portal)

8. DATA MODEL
================================================================================

  USERS
    id              : UUID (primary key)
    name            : string
    email           : string (unique, @nssce.ac.in)
    role            : enum [ADMIN, PRINCIPAL, HOD, CLUB_HEAD, STUDENT]
    department_id   : FK -> DEPARTMENTS
    roll_number     : string (for students)
    created_at      : timestamp

  DEPARTMENTS
    id              : UUID
    name            : string (e.g., "Computer Science & Engineering")
    code            : string (e.g., "CS")
    hod_user_id     : FK -> USERS

  CLUBS
    id              : UUID
    name            : string
    type            : enum [PROFESSIONAL, INNOVATION, SOCIAL, CULTURAL, SPORTS]
    head_user_id    : FK -> USERS

  VENUES
    id              : UUID
    name            : string
    department_id   : FK -> DEPARTMENTS (determines which HOD approves)
    capacity        : integer
    features        : JSON {ac, projector, smartboard, pa_system}
    svg_element_id  : string (ties to the campus map SVG element)

  EVENTS
    id                        : UUID
    title                     : string
    description               : text
    club_id                   : FK -> CLUBS
    club_head_id              : FK -> USERS
    venue_id                  : FK -> VENUES
    start_time                : timestamp
    end_time                  : timestamp
    expected_attendance       : integer
    category                  : enum [TECHNICAL, CULTURAL, SPORTS, SOCIAL,
                                      WORKSHOP]
    ktu_activity_points_cat   : string (nullable)
    status                    : enum [DRAFT, PENDING_HOD, PENDING_PRINCIPAL,
                                      APPROVED, REJECTED, COMPLETED, ARCHIVED]
    special_requirements      : text
    created_at / updated_at   : timestamp

  APPROVALS
    id              : UUID
    event_id        : FK -> EVENTS
    approver_id     : FK -> USERS
    approver_role   : enum [HOD, PRINCIPAL]
    action          : enum [APPROVE, REJECT]
    remark          : text (mandatory)
    actioned_at     : timestamp

  REGISTRATIONS
    id              : UUID
    event_id        : FK -> EVENTS
    student_id      : FK -> USERS
    registered_at   : timestamp
    status          : enum [REGISTERED, WAITLISTED, CANCELLED]
    attended        : boolean (default: false)

  CERTIFICATES
    id                : UUID
    registration_id   : FK -> REGISTRATIONS
    type              : enum [PARTICIPATION, COMPLETION]
    verification_code : string (unique, for QR)
    issued_at         : timestamp

  NOTIFICATIONS
    id              : UUID
    user_id         : FK -> USERS
    type            : enum [SUBMISSION, APPROVAL, REJECTION, REMINDER,
                            REGISTRATION]
    message         : text
    event_id        : FK -> EVENTS
    read            : boolean
    created_at      : timestamp

9. EDGE CASES & BUSINESS RULES
================================================================================

  #  | Scenario                                      | System Behavior
  ---|-----------------------------------------------|-------------------------
  1  | Venue has PENDING (not approved) event in      | Venue shown as yellow.
     | same time slot                                 | Still selectable. If
     |                                               | both approved, admin
     |                                               | notified for resolution.
  ---|-----------------------------------------------|-------------------------
  2  | Club Head resubmits with same venue after      | New approval cycle
     | rejection                                      | starts; old trail kept.
  ---|-----------------------------------------------|-------------------------
  3  | Event time changes after HOD approval but      | Club Head must
     | before Principal approval                      | re-submit (Principal
     |                                               | approval resets).
  ---|-----------------------------------------------|-------------------------
  4  | Student registered but didn't attend           | No certificate issued;
     |                                               | marked as "Absent".
  ---|-----------------------------------------------|-------------------------
  5  | Club Head is also a student                    | Dual role allowed;
     |                                               | system permits both.
  ---|-----------------------------------------------|-------------------------
  6  | Principal is also HOD of a department          | Can perform HOD duties
     |                                               | AND final approvals.
  ---|-----------------------------------------------|-------------------------
  7  | Event cancelled after approval                 | Club Head can cancel;
     |                                               | all registered students
     |                                               | notified; venue freed.
  ---|-----------------------------------------------|-------------------------
  8  | Venue capacity reached                         | New registrations go
     |                                               | to Waitlist; first
     |                                               | waitlisted notified on
     |                                               | cancellation.
  ---|-----------------------------------------------|-------------------------
  9  | Multiple clubs request same venue, same time   | First submitted gets
     |                                               | priority; second gets
     |                                               | conflict warning.
  ---|-----------------------------------------------|-------------------------
  10 | Club Head leaves/graduates                     | Admin reassigns Club
     |                                               | Head role to another.

10. KTU ACTIVITY POINTS INTEGRATION
================================================================================

KTU requires students to earn activity points for graduation.

This system will:
  - Tag each event with a KTU activity points SEGMENT:
      Segment 2 : Professional Self-Initiatives
      Segment 6 : Cultural & Sports
      (etc.)
  - Track student attendance (verified participation)
  - Generate semester-wise activity points report per student
  - Export in a format compatible with KTU e-Governance portal submission

This directly saves administrative time at semester end and is a key
differentiator for this system.

                                     |            |        | use policy

                                     |            |        | reminder after 48 hrs

                                     |            |        | constraint + locking

                                     |            |        | endpoint
